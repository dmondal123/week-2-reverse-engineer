# Insights paper: LlamaIndex vs Haystack under a framework-independent release contract

> **Status: final (2026-08-24), ready for submission.** All figures come from canonical artifacts: controlled run `task6-20260824T064738` and failure injection runs `failure-injection-20260824T093551` + `failure-injection-20260824T093605` (`artifacts/results/*.json`; EV-T9-006). Items marked UNKNOWN or LIMITATION require review before release.

## 1. Executive claim (150–250 words)

**Production decision: combine — run RAG pipelines on a single framework while keeping identity, release validation, and atomic promotion outside both frameworks.** Under fixed configuration, LlamaIndex and Haystack delivered observed-similar retrieval quality in this run (recall@5 = 1.0 and MRR 0.87–0.90 across all four framework × retriever conditions, run `task6-20260824T064738`, `artifacts/results/controlled-summary.json`); every answer cited only correct sources (citation source correctness = 1.0 in all 20 case runs) — a provenance property of our external identity contract, not evidence that answers are semantically complete (required-phrase coverage is only 0.73–0.80). Framework choice is therefore not the decisive risk; **the most important finding is that neither framework prevents mixed-version answers on its own** — both lack any native immutable-release concept (provenance matrix rows `corpus_version` = lost at index-time for both) — while an external release layer that validates corpus files AND a stored index inventory rejected a partial v2 promotion with the active pointer untouched and provably served only one release per query (`artifacts/results/failure-injection.json`, 9/9 assertions true). Confidence is high for the release finding (source + runtime evidence converge), medium for framework preference (single repetition, five synthetic cases). Consequence: invest engineering in the release mechanism and explicit-configuration discipline, not in framework switching; buy further runtime repetitions to chase the remaining required-phrase-coverage gap (0.73–0.80), the current top open observation.

*(Word count of this claim block: ≈195.)*

## 2. Decision context and scope

The organization must choose how to build retrieval-augmented answering over versioned internal policies where a stale or mixed corpus version producing a wrong answer is a compliance incident, not an inconvenience. Two candidate frameworks were compared: LlamaIndex and Haystack, pinned at llama_index@d8021225eb7e7b276d5ceb476b0a4650240f27f8 and haystack@c7cb46c0f28ad1984f60e5d3e9404b124a221437 respectively (`config/repository-manifest.json`; EV-T2-001, EV-T2-002). All model calls ran locally through Ollama using `nomic-embed-text` (digest `0a109f422b47…`, EV-T5-001) and `qwen3:4b-instruct-2507-q4_K_M` (digest `0edcdef34593…`, EV-T5-002); no hosted APIs were used.

The investigation design follows one rule that shaped everything downstream: **every claim must be bound to either a pinned source line or a saved runtime artifact**. Source tracing preceded any conclusion about framework internals; the three hypotheses were written and timestamped before any implementation file was opened (`evidence/hypotheses.md`), so the paper can distinguish what was predicted from what was found. The evaluation contract (`eval/cases.json`) contains five deliberately discriminating cases: a multi-fact case requiring three sources at once, an exact-identifier case (rule AP-50 / $50 threshold), a semantic paraphrase case, an obsolete-source trap where the superseded memo must not ground the answer, and a version-change case whose correct answer differs between v1 ($25/day) and v2 ($30/day). The trap case is what makes corpus-version mixing observable in answers rather than only in metadata.

Scope was deliberately narrow: six-document v1 corpus derived to five-document v2, five discriminating evaluation cases, one shared pipeline contract implemented by two adapters, one controlled variable (retriever kind: BM25 vs dense), and one injected failure mode (partial reindex promotion). Out of scope: UIs, external vector databases, hosted services, additional frameworks, and statistical generalization beyond the synthetic corpus. This scope decision is itself an interpretation: we treat pipeline equivalence under identical configuration as the fair comparison target, not framework-native showcases, because production reproducibility requires knowing exactly what each stage does.

**Two layers, kept separate throughout this paper:** *framework-native behavior* is what the pinned LlamaIndex/Haystack code does on its own — ambient defaults, id generation, splitting, retrieval ranking — and carries all hypothesis weight; the *shared wrapper* is our own normalization layer (identity assignment, token-window chunking, packing, tracing, release control) and is identical across both columns of every comparison. Any capability attributed to the wrapper is explicitly labeled as such below; nothing measured under the 2×2 design varies by wrapper, so cross-framework differences are framework-native differences by construction. A consequence of this narrowness is honesty about transferability: results describe these pinned commits, this synthetic policy corpus, and this local Ollama host — nothing more.

## 3. Competing hypotheses

Three hypotheses were written before any source tracing (`evidence/hypotheses.md`, timestamped 2026-08-22T10:50:42Z):

- **H1 — LlamaIndex hidden convenience state:** global `Settings` and convenience defaults conceal material retrieval behavior unless every resolved value is captured.
- **H2 — Haystack graph visibility vs transformation risk:** the explicit component graph improves observability while converters/splitters may still invisibly transform identity/metadata.
- **H3 — frameworks do not provide atomic reproducible releases alone:** neither validates complete versioned manifests nor atomically promotes a query-visible pointer without external logic.

Outcome after tracing and runtime: H1's mechanism was confirmed at source level (EV-T4-002, EV-T4-003, EV-T4-004, EV-T4-005) and mitigated in our adapters by explicit configuration plus settings snapshots; H1 remains OPEN because the hypothesis concerns framework behavior, not our mitigation. **H2 was WEAKENED by counterevidence**: the observability half held (explicit graph execution, EV-T4-010), but transformation risk proved stronger than predicted — Haystack children are new Documents whose ids are re-derived from content including the embedding vector, with the parent id dropped (EV-T4-007, EV-T4-008). H3 remains OPEN with strong converging support: source tracing found no native release concept in either write path, and the failure injection demonstrated both failure prevention and recovery through external controls only. Full table: `paper/hypothesis-evidence.md`.

A methodological note on discrimination: each hypothesis was written with a rejection condition before tracing, which forced the investigation to look for disconfirming evidence rather than confirmatory patterns. For H3 this meant actively searching both frameworks' write paths for any native manifest-validation or atomic-pointer mechanism; finding only Haystack's DuplicatePolicy as the closest construct (HS-2/EV-T4-006) is negative evidence recorded in the provenance matrix's `corpus_version` rows ("lost" for both frameworks at index-time), not merely an absence of mention.

The required rejected/weakened explanation is the pre-trace reading that "graph visibility makes identity transformations low-risk." The pinned source shows visibility and identity safety are independent properties: the graph exposes component boundaries while id regeneration driven by embedding fingerprints happens inside a visible component yet is invisible unless its fingerprint inputs are inspected (EV-T4-007, EV-T4-008).

## 4. Architecture reconstruction

Both index-time paths were traced from their public entry points to storage; line references are commit-bound at the SHAs above (`evidence/source-references.md`).

**LlamaIndex index-time (fact):** `VectorStoreIndex` is the public entry point; `_build_index_from_nodes` and `insert_nodes` are the write paths (LI-1, EV-T4-001). Embedding falls back to the process-global `Settings.embed_model` when not passed explicitly (LI-2/EV-T4-002), default chunk size is 1024 tokens and default top-k is 2 via module constants (LI-4/EV-T4-003), and `Settings` itself is a lazily-initialized singleton holding llm/embed/parser/callbacks/tokenizer (LI-5/EV-T4-004). Node ids are freshly generated during parsing; provenance survives only if the parser copies it (LI-9). The response synthesizer repeats the same fallback pattern for the LLM (LI-6/EV-T4-005).

**Haystack index-time (fact):** `DocumentWriter.run` is the public write path into an in-memory store where DuplicatePolicy.NONE becomes FAIL on duplicate ids (HS-1, HS-2/EV-T4-006). Splitter defaults are constructor-local — word/200/0 — unlike LlamaIndex's ambient constants (HS-3/EV-T4-009 context). Splitting creates new Documents whose ids are re-hashed from child content; parent ids do not survive as fields (HS-4/EV-T4-007). Document.id is a SHA-256 fingerprint over text/meta/embedding with sorted keys (HS-5/EV-T4-008).

**Query time:** LlamaIndex resolves query embeddings and callback managers from the same ambient state and returns store-ordered scores (LI-7, LI-8); `VectorStoreRetriever._retrieve` computes the aggregate query embedding when absent and delegates to the vector store, with constructor default `similarity_top_k = DEFAULT_SIMILARITY_TOP_K = 2` unless overridden (LI-8/EV-T4-003 context) — meaning a caller that forgets top-k silently retrieves two chunks, a failure mode our five-chunk experiment configuration would have exposed only through the resolved-settings snapshot. Haystack executes an explicitly connected graph (HS-6/EV-T4-010) with BM25 ranking computed inside the document store itself rather than in the retriever component, `scale_score=False` by default so raw BM25 scores flow through unchanged (HS-7, HS-10/EV-T4-009), dense retrieval with configurable runtime filters and REPLACE/MERGE filter policies (HS-8), and citation assembly via `AnswerBuilder` that inherits whatever identity survived splitting (HS-9).

Documented behavior in both frameworks is corroborated by their own test suites at the pinned SHAs — splitter and writer tests on the Haystack side (REF-T1, REF-T2) and vector-store retriever tests on the LlamaIndex side (REF-T3) — which satisfies the triangulation requirement that architectural claims rest on more than one evidence form (EV-T4-011).

It is worth reading the provenance matrix at field level, because the pattern of loss differs between the frameworks even where the headline classification matches. Neither framework stores a content hash of a retrieved chunk natively — LlamaIndex identity is node-id based (LI-3), and Haystack's hash exists only inside `_fingerprint` for id generation (EV-T4-008) — so content-level verification of a retrieved chunk is impossible without wrapper bookkeeping. `source_span` splits the two: LlamaIndex's SentenceSplitter does not expose character spans by default, while Haystack's DocumentSplitter records `splits_start_idxs`, making position metadata available when configured (REF-T1). `embedding_id` is transformed in both at index-time — LlamaIndex resolves the embedder from ambient state unless overridden (EV-T4-002), and neither records the model digest alongside stored vectors, which is why our contract pins digests in configuration and snapshots resolved settings instead (`config/experiment.json`). Finally, `citation_id` is classified transformed at query-time for both: the synthesizer/AnswerBuilder cite whatever nodes they received, inheriting any index-time loss — which is precisely why citation assembly was moved into the shared adapter layer. Full 12-field × 2-stage matrix: `evidence/provenance-matrix.csv`.

**Adapter normalization:** because native ids and provenance diverge as described above, both adapters normalize every candidate to the shared contract fields — source/document/chunk ids derived from source bytes and spans (`src/rag_compare/identity.py`), text, span, score, original rank, metadata, and release ID — and emit one frozen-schema stage event per boundary into an append-only, fsync-per-event JSONL trace (`src/rag_compare/trace.py`). This wrapper-level bookkeeping is precisely why citation spans resolve correctly even though neither framework preserves span offsets natively in both paths (provenance matrix rows `source_span`: lost for LlamaIndex, preserved only optionally for Haystack).

**The release boundary (fact, external to both):** neither framework appears anywhere in the release mechanism. Our layer validates file sets, SHA-256 hashes, counts, schema, and embedding identity against a manifest, then promotes with one atomic pointer replacement (`src/rag_compare/release.py`). Query callers capture the active release once and every retrieval branch filters chunks by the captured release, raising on any foreign chunk. Diagram: `paper/architecture.mmd`. Provenance classification for all 12 required fields at both stages: `evidence/provenance-matrix.csv`.

## 5. Experiment design

Run `task6-20260824T064738` executed a 2×2 design — {llamaindex, haystack} × {bm25, ollama_dense} — over all five evaluation cases with everything else frozen: token-window chunking 200/40, top-k 5, temperature 0, seed 0, prompt hash `e029718b…` (the remediated prompt requires explicit `[n]` citation markers), context budget 1200 tokens, tie-break score-desc-then-chunk-id-asc (`config/experiment.json`; input hashes recorded in the summary's `input_hashes`). Chunking is a wrapper-level stage, identical in all four columns: a shared cl100k_base token-window splitter (200-token windows, 40-token overlap; exact char spans verified by tests/test_chunking.py) — every document body fits inside one window at this corpus size. Each release manifest additionally validates a query-time contract: retriever conditions/top-k/tie-break, reranker, packing/citation mode, generator model+digest, prompt SHA-256, and sampling options, so changing any of them requires a new release. `artifacts/raw/task6-20260824T064738/`; each framework/version build also persists its full release manifest and chunk inventory under the run directory. Control validation programmatically compared manifests across conditions: within each framework pair the build-manifest SHA-256 is identical, so the only material difference was retriever kind; `control_validation.failures = []`. A frozen quality-gates block (recall floor, zero forbidden citations, full release consistency) was pinned before execution and passed; summary status is `passed` only when controls AND gates pass.

The failure injection (Task 7 revision, executed through BOTH adapters as runs `failure-injection-20260824T093551` llamaindex / `failure-injection-20260824T093605` haystack, 9/9 assertions true each) activated v1, indexed half of v2 into staging, attempted promotion, queried all cases, completed v2, validated, promoted atomically, and re-queried — preserving separate first-failure and post-recovery traces per framework (`artifacts/raw/failure-injection-{llamaindex,haystack}-trace.jsonl` and `-post-recovery-trace.jsonl`). Promotion validation verifies both the corpus files AND a stored hash-bound chunk inventory whose entries must recompute from the on-disk corpus; unit-level negative tests prove a complete-files/empty-index release cannot be validated (`tests/test_release.py`). Earlier superseded artifacts are archived at `artifacts/raw/archive-pre-remediation-20260824/` (see Section 9 for protocol notes).

Metrics were computed per case and never collapsed into one score: recall@k, MRR, forbidden-source handling over the model-cited sources, citation source/span correctness, required-phrase coverage of the answer, per-stage latencies including capture-release, release-filter, rerank, pack, and generate stages, total latency, and release consistency (`artifacts/results/controlled-results.csv`; 20 case rows). Wall clock was 26.787 s for all four conditions.

## 6. Results and evidence

**Retrieval quality (fact):** recall@k = 1.0 in every condition and case; MRR = 0.90 everywhere except the obsolete-source trap case, where the obsolete memo outranks the current policy (MRR 0.5 for three conditions, 0.333 for haystack:bm25). Dense retrieval does not consistently avoid the trap. With n=1 repetition this is an observation, not a conclusion (LIMITATION).

**Latency (fact):** generation dominates — mean generate latency 1176–1468 ms versus retrieval 3.3–27.2 ms per condition; total means ranged 1187.3 ms (haystack:bm25) to 1491.5 ms (llamaindex:ollama_dense). Differences between frameworks are small relative to generation variance and single-host conditions. LlamaIndex nodes enter the index with pre-computed embeddings computed by the shared wrapper, so store-stage latency contains no second embedding pass in either column.

Per-condition means from `artifacts/results/controlled-summary.json` (single repetition):

| Condition | MRR | recall@5 | coverage | retrieve ms | generate ms | total ms |
|---|---|---|---|---|---|---|
| haystack:bm25 | 0.867 | 1.0 | 0.73 | 11.4 | 1175.8 | 1187.3 |
| haystack:ollama_dense | 0.900 | 1.0 | 0.80 | 27.2 | 1304.0 | 1331.3 |
| llamaindex:bm25 | 0.900 | 1.0 | 0.80 | 3.3 | 1236.9 | 1240.3 |
| llamaindex:ollama_dense | 0.900 | 1.0 | 0.80 | 22.9 | 1468.5 | 1491.5 |

Analysis: dense retrieval costs roughly 2–7× more latency than BM25 (11.4→27.2 ms on haystack, 3.3→22.9 ms on llamaindex) yet buys no measurable quality gain here — both retrievers reach recall@5 = 1.0, and the MRR spread (0.867 vs 0.900) traces entirely to the obsolete-source trap case, not to retriever kind or framework. Coverage is likewise retriever-independent: it moves with the case mix (trap and multi-fact cases drag it down), not with the retrieval condition. The only stage where the frameworks separate measurably is native retrieval cost (haystack BM25 11.4 ms vs llamaindex BM25 3.3 ms), which is irrelevant next to generation's three-orders-of-magnitude dominance.

**Citations (fact, with an explicit reading boundary):** citations are derived from the answer's `[n]` markers in a separately traced citation stage, so the metrics measure what the model actually cited. Citation source correctness = 1.0 in all 20 case runs, and span correctness = 1.0 under byte-level verification: each cited [start, end] span is re-sliced from the immutable corpus bytes on disk and must reproduce exactly the text bound to the cited chunk id (`src/rag_compare/metrics.py`; tampered-candidate rejection is unit-tested).

What these 1.0s do and do not establish: they validate the wrapper's identity contract against framework-native id regeneration — cited chunks exist, belong to the active release, and their spans resolve to exact corpus bytes. They say nothing about whether the answer's claims are semantically supported by those spans. That question is answered by the independent citation-support and required-phrase-coverage metrics, which read 0.73 across conditions and 0.73–0.80 respectively: cited spans do not always contain every expected fact. An answer can therefore be perfectly sourced and still incomplete — correct provenance is necessary, not sufficient, for answer quality. Mean 1.0–1.2 citations per answer shows disciplined, minimal citing. **Remaining observation:** required-phrase coverage is 0.73–0.80, i.e., the generator sometimes omits an expected fact while citing correctly; reported per case and deliberately not gated pending diagnosis.

The per-case decomposition adds three nuances the condition means hide.

First, on the obsolete-source trap case all retrievers rank the obsolete memo second or worse (MRR 0.5 in llamaindex:bm25, llamaindex:ollama_dense, and haystack:ollama_dense; 0.333 for haystack:bm25), i.e., lexical and dense scoring fail the trap similarly under this corpus size — yet trap-case required-phrase coverage is 1.0 in every condition. The answers are version-correct even when ranking is imperfect, because correct behavior here comes from prompt discipline plus release-filtered context rather than retrieval quality; the MRR penalty reflects the obsolete memo's presence in the ranked list, not a wrong answer.

Second, the coverage shortfall is systematic, not noisy: it lives almost entirely in two case types. The semantic-paraphrase case and the version-change case score exactly 0.5 in all four conditions, and the multi-fact case drops to 0.667 only on haystack:bm25 (1.0 elsewhere). In other words, every condition omits one of two expected facts whenever the query paraphrases rather than quotes the corpus, and every condition reports only the v2 limit's day-rate without the second expected fact on the version-change case. A failure that replicates identically across frameworks, retrievers, and seeds points at the shared prompt/context-packing layer — wrapper-owned, identical in all columns — not at framework-native retrieval. This reframes the top open observation: buying more repetitions will not move it; changing the packing strategy or required-phrase prompting will.

Third, generation latency is driven by case difficulty, not condition. Within-condition generation spans are enormous relative to between-condition differences: 682 ms (haystack:ollama_dense, exact-identifier) to 3,038 ms (same condition, multi-fact) — a 4.5× spread inside one condition — while condition mean totals differ by at most ~300 ms. The two multi-fact dense runs (2 events, ~3 s each) show the model spending proportionally more time as cited-source count rises from 1 to 2. Any production capacity plan built from the condition means alone would underestimate peak generation cost by a factor of ~2.5.

**Failure injection (fact):** partial v2 promotion was rejected ("corpus file set does not match the release directory"); the active pointer remained byte-identical (`{"release_id": "v1"}`); all Phase A queries returned only v1 chunks on both retrieval branches with no v2 leakage; the mixed-release filter raised on a foreign chunk; complete v2 promoted atomically to `{"release_id": "v2"}`; Phase B queries returned only v2 chunks and deleted v1 content (office-snacks) never resurfaced. All nine assertions true for EACH framework — 18/18 total (`artifacts/results/failure-injection.json`, combined; per-framework summaries alongside). Validation additionally verifies the stored index inventory against contract-recomputed identities; unit tests prove empty-index, missing-inventory, and stale-ID releases are rejected (`tests/test_release.py`). No unexpected mixed-version failure occurred, so no corrective release-control change was needed.

Full tables: `paper/experiment-results.md`; risk/control mapping: `paper/risk-control.md`.

## 7. Production analysis

*Interpretation:* five findings matter for production more than the framework comparison itself; a seven-dimension production checklist (cost, safety, privacy, scale, idempotency, backpressure, operability) follows below.

First, **identity is not preserved natively end-to-end in either framework.** The provenance matrix shows chunk/document ids synthesized or transformed at index-time in both, `source_version`/`schema_version`/`release_id` lost entirely in both, and source spans lost entirely in LlamaIndex. Any audit requirement ("show me the exact policy text behind this answer") therefore depends on wrapper-level bookkeeping. Our contract assigned stable ids from source bytes and spans, achieving citation-span correctness 1.0 — but that correctness belongs to the wrapper, not the framework, and it certifies provenance only: it does not establish that answers are semantically complete (coverage 0.73–0.80).

Second, **ambient configuration is a reproducibility hazard specific in degree, not in kind.** LlamaIndex concentrates it in one singleton (EV-T4-004); Haystack distributes it across constructor defaults (EV-T4-009). Both are manageable with explicit configuration plus snapshots, which is exactly what made the controlled experiment's control validation pass. A team unwilling to enforce that discipline should treat LlamaIndex convenience APIs as a standing risk (H1).

Third, **release safety came exclusively from the external mechanism**, confirming H3's prediction against both write paths. The practical consequence is organizational: corpus rollout procedures should be owned by the platform layer and tested by failure injection, independent of whichever framework renders the answers.

Fourth, a note on what the latency data does and does not license. Per-condition means differ by up to ~304 ms total (1187.3–1491.5 ms), but the spread sits almost entirely inside the generation stage, whose variance across individual cases in the same condition exceeds several hundred milliseconds (per-case rows in `artifacts/results/controlled-results.csv`). With one repetition, no ranking of frameworks or retrievers by speed is defensible; the only robust latency statement is structural: retrieval and all wrapper stages (release capture, filtering, packing) are together two to three orders of magnitude cheaper than generation, so end-to-end optimization effort belongs in the generation budget, not the retrieval path. This is an interpretation grounded in the recorded stage decomposition, not a benchmark result.

Fifth, the version-change case demonstrates end-to-end correctness of the whole stack in the positive direction: after v2 promotion, the model answered "$30 per travel day" citing `travel-wifi-current`, whereas Phase A against captured v1 answered "$25" — the same query returning version-correct answers purely because the release pointer moved atomically between runs (`artifacts/results/failure-injection.json`, phases A/B excerpts). That is the observable payoff of the release mechanism.

### 7.1 Production-readiness checklist

*Interpretation:* each dimension below is assessed against what this investigation actually measured plus explicit engineering judgment; none of these dimensions was benchmarked at production load.

- **Cost.** The recorded stage decomposition shows generation dominates: retrieval plus all wrapper stages are two to three orders of magnitude cheaper than generation (per-stage rows in `artifacts/results/controlled-results.csv`). The remediation also removed a real cost defect in our wrapper: LlamaIndex originally re-embedded every chunk at index build; passing pre-computed embeddings into `VectorStoreIndex` halves embedding spend per rebuild. Production consequence: cost control belongs in (a) embedding reuse on rebuilds — only changed chunks should be re-embedded, which the chunk-id contract makes possible — and (b) generation budget caps, not retriever tuning. Local Ollama hosting shifts API spend to hardware amortization, but that trade is unmeasured here.
- **Safety.** Release safety came exclusively from the external mechanism: 9/9 failure-injection assertions true for both frameworks, including rejection of a partial promotion with the pointer untouched (`artifacts/results/failure-injection.json`). Answer-safety metrics (zero forbidden-source citations, citation source/span correctness 1.0) were met under frozen quality gates, but these are provenance guarantees, not content guarantees: required-phrase coverage 0.73–0.80 means answers can still omit expected facts — a semantic-completeness gap that must be gated separately before any user-facing rollout.
- **Privacy.** Everything ran against a local Ollama host with a synthetic corpus, so no prompt or document left the machine. Neither framework adds privacy controls of its own: both send full packed context to the generator verbatim, and neither redacts or scopes metadata. If corpus documents carried PII, the provenance matrix's lost fields (`source_version`, `schema_version`) mean retention/erasure policies could not be enforced through framework state alone; the wrapper's immutable-release namespaces are the only viable enforcement point (delete a release namespace and its content becomes unreachable — demonstrated by the deleted-v1 assertion).
- **Scale.** All measurements use six documents and an in-memory store on one host; nothing here licenses claims about sharded vector stores, concurrent writers, or index sizes beyond memory. Structurally, the design scales in the right places: identity is content-derived (no central id allocator), releases are immutable directories (replicable), and the active pointer is a single atomic file (trivially cached). The unscale parts are the in-memory stores themselves and single-host Ollama; both would need replacement before production traffic, without touching the contract layer.
- **Idempotency.** Builds are deterministic by construction: chunk ids derive from document id + span + text hash, so re-running a build over identical bytes yields identical ids and identical inventory hashes (control validation confirmed byte-identical build manifests across BM25/dense conditions). Promotion is idempotent because validation rejects anything that does not match the manifest before the pointer moves. Re-running the *same* release promotion twice is safe; promoting two *different* builds claiming the same release_id is correctly rejected (manifest/query-contract mismatch assertion). Retry-safe ingestion therefore holds within a release but depends on the external validator, not the frameworks.
- **Backpressure.** Unmeasured — this is the weakest dimension in the study. The pipeline is fully synchronous end-to-end; there is no queue, no admission control, and no load shedding between retrieve→rerank→pack→generate. Under bursty load, Ollama generation latency (the dominant stage, hundreds of ms variance between cases in the same condition) will serialize callers. Recommendation carried into the ADR next-evidence list: test promotion and query under concurrency before production; add bounded queues in front of generation with explicit timeout and degradation behavior (e.g., return citations without synthesis rather than block).
- **Operability.** The strongest non-functional result. Every stage emits a JSONL trace event with resolved configuration, durations, input/output ids, and release binding; run status is gated by frozen quality checks, so "passed" is mechanically meaningful. Failure injection doubles as an operational drill with preserved traces. Gaps: no live monitoring/metrics endpoint, no alerting, single-host logs only, and rollback relies on repointing the release pointer manually — cheap and atomic, but unaudited unless the pointer change itself is logged.

## 8. Decision and ADR

Decision: **combine** — detailed alternatives, consequences, reversibility, and next-evidence analysis are recorded in `paper/decision.adr.md`. Summary: adopt one framework for pipeline ergonomics (Haystack preferred marginally for inspectable defaults and explicit graph observability, per EV-T4-009/EV-T4-010; the measured quality difference is nil), and adopt the framework-independent release recommendation separately: immutable namespaces, manifest validation, single-capture release filtering, atomic promotion. Reversibility is high because both adapters implement one shared contract and the release layer is already framework-free. Next evidence worth buying: add repetitions/cases before latency claims, and test promotion under concurrent queries.

On alternatives, briefly: pure **adopt** of either framework was rejected because reproducibility gaps are complementary, not framework-specific — LlamaIndex concentrates ambient-state risk (driver 1 above) while Haystack concentrates silent identity transformation at split time (EV-T4-007/EV-T4-008) — so neither choice removes the need for external controls. **avoid** (hand-rolled pipelines) was rejected because both frameworks already passed control validation with zero configuration drift over BM25 and dense paths against a local Ollama host, and rebuilding them would not address the missing release concept (H3) anyway. **investigate**-only was rejected as a decision because the release mechanism — the actual risk control — is framework-independent and already implemented and exercised; further framework investigation can proceed in parallel without blocking it. Reversibility details, consequences, and the priced next-evidence list are recorded in `paper/decision.adr.md`.

## 9. Limitations and unknowns

- **LIMITATION:** five evaluation cases, one repetition per condition, synthetic six-document corpus, single local host. No statistical significance is claimed for any cross-framework difference.
- **OBSERVATION:** required-phrase coverage is 0.73–0.80 — the generator sometimes omits an expected fact while citing correctly; this, not citation sourcing, is the open quality gap.
- **LIMITATION:** the forbidden-source metric scores model-cited sources (a violation is citing a forbidden source, not retrieving it); obsolete sources remain intentionally indexed per `config/experiment.json` metadata_filter note.
- **LIMITATION:** repository SHA/remote metadata in `config/repository-manifest.json` was verified locally via `git rev-parse` / `git remote` on the pinned clones (see each entry's `verification_status`); it is user-supplied in origin but commit-bound to the audited checkouts. (The earlier collaboration-log entry calling this metadata "locally unverified" is superseded by the 2026-08-24 verification entry.)
- **UNKNOWN:** behavior under concurrent query/promotion interleaving; atomicity was exercised sequentially.
- **LIMITATION:** Task 7 reruns occurred without explicit human approval during the original run (protocol deviation, logged in `week2/AI_COLLABORATION.md`); the post-remediation rerun was explicitly approved, and pre-remediation artifacts are archived at `artifacts/raw/archive-pre-remediation-20260824/`, not deleted.
- Latencies reflect one Ollama host and the pinned qwen3:4b quantization; they are not transferable figures.
- **SCOPE NOTE:** parsing/chunking/identity run in a shared normalization layer by design (ARCHITECTURE.md wording corrected after review); the experiment therefore compares framework-native indexing and retrieval, not ingestion abstractions.
